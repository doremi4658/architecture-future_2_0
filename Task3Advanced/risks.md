# Карта рисков трансформации «Будущее 2.0»

## Методология оценки

- **Вероятность**: Низкая (1), Средняя (2), Высокая (3).
- **Влияние**: Низкое (1), Среднее (2), Высокое (3).
- **Уровень риска** = Вероятность × Влияние:
  - 1..2 — Зелёный (допустимый),
  - 3..6 — Жёлтый (требует смягчения),
  - 7..9 — Красный (недопустим без дополнительных мер).

## План управления рисками

### R01 — Неверные границы доменов
- **Мера**: Проведение Event Storming воркшопов с ключевыми стейкхолдерами, итеративное уточнение границ в ходе пилотного этапа (первые 6 месяцев). Техническое решение — строгий контракт событий в Schema Registry, запрещающий обход событийной шины.
- **Тип**: Управленческий + Технический.

### R02 — Консистентность в асинхронной модели
- **Мера**: Использование паттерна Transactional Outbox в критичных сервисах, внедрение Dead Letter Queue (DLQ) с автоматическим перевыставлением событий, а также компенсирующих транзакций для финансовых операций. Документирование SLA по консистентности для каждого потока.
- **Тип**: Технический.

### R03 — Лавинообразный отказ Event Hub
- **Мера**: Автоматическое масштабирование брокеров Kafka, настройка throttling и мониторинга с алертами (Consumer Lag, грязные топики), использование Quotas. Резервирование через мульти-AZ развёртывание.
- **Тип**: Технический.

### R04 — Потеря данных при миграции
- **Мера**: Двухфазная стратегия: сначала параллельное ведение данных в старом DWH и новом Data Lake с автоматической сверкой дайджестов. Разработка процедур обратной загрузки в «мост совместимости». Пилотная миграция некритичных данных.
- **Тип**: Технический + Управленческий (контрольные точки).

### R05 — Производительность Object Storage
- **Мера**: Использование колоночного формата (Parquet) с партиционированием, предварительный агрегат в потоковом процессоре, кэширование Trino, выбор SSD-хранилища для активных витрин.
- **Тип**: Технический.

### R06 — Несовместимость легаси-протоколов
- **Мера**: Разработка антикоррупционного слоя (Camel Bridge) с адаптерами для каждого старого протокола (JDBC, SOAP). По мере миграции старые источники подключаются напрямую к Kafka после модернизации.
- **Тип**: Технический.

### R07 — Сопротивление пользователей
- **Мера**: Поэтапный переход с обучением и регулярной обратной связью. Внедрение «песочницы» для знакомства с порталом, сохранение ограниченного доступа к PowerBuilder на переходный период. Назначение «чемпионов» из числа пользователей.
- **Тип**: Управленческий.

### R08 — Нехватка компетенций
- **Мера**: План обучения, наём специалистов по Kafka/Streaming, партнёрство с внешними консультантами на начальном этапе. Создание внутреннего центра компетенций (CoE) по Data Platform.
- **Тип**: Управленческий + Технический (референсные архитектуры, шаблоны).

### R09 — Зависимость от облачного провайдера
- **Мера**: Использование облако-независимых компонентов (Kafka Kubernetes Operator, Trino, MLflow), абстрагирование через Docker/K8s. Регулярное тестирование миграции на альтернативное облако или bare‑metal.
- **Тип**: Архитектурный (технический).

### R10 — Нарушение регуляторных требований
- **Мера**: Изоляция медицинских данных в отдельном облачном проекте с шифрованием (KMS), аудит доступа, регулярный пентест. Соблюдение 152-ФЗ и стандартов ЦБ РФ через гео-распределённое размещение и резервное копирование.
- **Тип**: Организационный + Технический (сертификация, DLP).
